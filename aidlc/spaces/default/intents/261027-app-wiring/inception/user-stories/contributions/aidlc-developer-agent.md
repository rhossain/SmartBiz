### 2. Is the US5.1 role table implementable with existing capabilities? Yes, with two notes

I checked every row against `src/auth/capability.ts` and the any-of `requiredCapability` shape already used in `src/router/routes.ts` / `src/orders/order-capability.ts`:

| Row | Gate (existing values only) | Roles it admits | Matches table |
|---|---|---|---|
| Read orders, customers, products, suppliers | `business.view` | all four | ✓ |
| Orders mutate; link consignments | `ORDER_MUTATE_CAPABILITIES` = any of `money.mutate.price`, `money.mutate.full` | Owner, Manager, Sales Staff | ✓ (already built) |
| Customers and notes | the same constant (a `CUSTOMER_MUTATE_CAPABILITIES` alias in a new `src/catalog/catalog-capability.ts`, mirroring `order-capability.ts`) | Owner, Manager, Sales Staff | ✓ |
| Products, variants, stock, suppliers | any of `business.edit`, `money.mutate.full` | Owner, Manager | ✓ (`business.edit` is redundant, since the Owner also holds `full`, but harmless) |
| Purchase cost | any of `money.mutate.full`, `money.mutate.cost` | Owner, Manager, Accountant | ✓ |
| Create invitations | `staff.invite` | Owner, Manager | ✓ (already enforced in `src/auth/invite.ts`) |
| Audit trail | `audit.view` | Owner, Manager, Accountant | ✓ (P-18 open question stays) |
| Business settings | `business.edit` | Owner | ✓, but only as a **screen route**: `/business` has no screen and no API endpoint in scope |

Notes that change the stories:

- **The purchase-cost row needs its own endpoint.** The gate is per route. If the Accountant's cost-only edit (AC3.4.4) lives inside the general product-edit endpoint, it becomes a field-level check that the route walk in AC5.1.1 cannot see. Proposal: `PATCH /api/products/:id/cost`, gated by any of `full`/`cost`, and the general edit endpoint gated by any of `business.edit`/`full`. Then the walk proves the Accountant gets 403 on the general edit and 200 on the cost edit.
- **The API route walk needs a server route table held as data**, typed like the client's `ReadonlyMap` with the same `requiredCapability` type, so `three-layer-gate-absence` can enumerate it (team.md: "walks the bun server's registered route table, not a hand-kept list"). This belongs in US1.1's server foundation (section 3).
- **Contradiction to resolve:** FR6.3 says "The **Owner** sets and edits each variant's current stock", while the US5.1 table and US3.5's actor ("As the Manager") give stock to Owner and Manager. Per `phases/inception.md` it must be resolved explicitly. I recommend following the table (Q2 answer A) and recording that FR6.3 is read as Owner and Manager.
- **Out-of-table but implied:** `acceptInvite` lets a Manager invite another Manager. The capability allows it. I flag it so that silence is not taken for a decision; it needs no change in this intent.

## Positions

- AGREE: Bolt split (Bolt 1 wiring, Bolt 2 catalog) — every catalog story depends only on Bolt 1 artifacts, and no Bolt 1 story needs a catalog table once order ids are UUID-only (D9).
- AGREE: US5.1 role table — every row maps to existing `Capability` values with the any-of `requiredCapability` shape already in `src/router/routes.ts`; no new Capability value is needed.
- AGREE: Security rules as ACs inside the stories they guard (Q6=A) — it keeps each guarantee next to the code that must uphold it, matching the MVP's CC-AC learning.
- OBJECT: US1.6 shows the reset link on the web screen — anyone at the shop laptop who types the Owner's email gets a working reset link and takes over the account. It also makes known and unknown emails respond differently, which contradicts AC1.6.2. Proposal: the screen always gives the same neutral message, and the one-time link is printed only by a local CLI command (`if (import.meta.main)` entry, same pattern as `src/db/migrate.ts`) run by whoever controls the machine. An Owner-signed-in "reset a staff password" (`staff.manage`) can follow later.
- OBJECT: US1.3, US1.7, US2.1, US3.4 and US4.1 as drafted — each exceeds 3 days on the existing code (section 3). Split them as proposed: US5.3 from US1.3, US1.7a, US2.1a/b, US3.7 from US3.4, US4.2 from US4.1.
- OBJECT: US5.2 as one story — AC5.2.1 cannot pass until Bolt 2, so Bolt 1 and the walking skeleton would have no end-to-end proof. Split into US5.2a (Bolt 1) and US5.2b (Bolt 2).
- OBJECT: US3.5 (Must) depending on US3.6 (Should) for the default supplier — a priority inversion. Promote US3.6 to Must, or give AC3.5.2 a "no supplier recorded" outcome.
- OBJECT: Hidden dependencies D1–D5 and D9 are not stated in any AC — without the auth-table grants, `users.business_id`, the session hash column, the pre-auth audit placement, the singleton business and UUID-only order ids, the stories as written either fail on real Postgres or block the Bolt 2 migration. Add them as ACs on the owning stories.
- OBJECT: FR6.3 ("the Owner sets stock") against the US5.1 table and US3.5 (Owner and Manager) — an unresolved contradiction that must be settled explicitly per `phases/inception.md`; I recommend following the table.
