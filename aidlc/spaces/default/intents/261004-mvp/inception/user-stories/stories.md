# SmartBiz BD — User Stories

> Generated by the User Stories stage of `intent 261004-mvp`. Anchors
> every MVP story to one or more `FR` IDs in `requirements.md` and
> preserves the inline NFR acceptance-criteria pattern from Q2
> (audit-immutability, role-gate, basis pill, recognition-basis
> completeness). MoSCoW split per Q3: Must-Have = the 9 table-stakes
> modules; Should-Have = the 3 phase-2 differentiators
> (Dashboard §5.10, Reports §5.11, AI Insights §5.12). Per Q4 stories
> are grouped by epic under 3 families: **Capture** (orders,
> customers, products, auth), **Settle** (payments, dues,
> settlements, restock, expenses), **Operate** (staff, settings,
> audit). Per Q5 every FR cluster has at least one story; NFRs are
> inlined as ACs.

## Story ID convention

- Epic family prefix: `US1` (Capture), `US2` (Settle), `US3` (Operate).
- Story ID: `US{family}.{seq}` (e.g. `US1.7` is the 7th story in
  the Capture family).
- AC ID: `AC{story-family}.{story-seq}.{criterion-seq}` (e.g.
  `AC1.7.3` is the 3rd AC on story `US1.7`).
- Deferral marker: `USx.y.D` for phase-2 differentiators that
  receive a stable ID but a deferred body (Q5: every FR cluster →
  at least one story; phase-2 stories carry `[Deferred]` and route
  to the phase-2 Delivery Planning stage).
- Persona tag: each story opens with `[P-Owner]`, `[P-Staff]`,
  `[P-Viewer]`, `[P-System]`, or a combination.

## Cross-cutting ACs (CC-AC)

These are the cross-cutting acceptance criteria that appear as
inline ACs on every relevant story (per Q2 decision). They are
listed here once so each story stays short.

- **CC-AC-AUDIT** Every money-mutating action appends an audit row
  carrying actor, business, entity, before/after values, and
  timestamp. The audit table is append-only at the DB role level
  (the application role holds `INSERT` only). [FR12.1] [FR12.3]
- **CC-AC-ROLE-GATE** A money screen renders for the current role
  only when the role's `capability.money` flag covers the figure
  shown. Tested by absence: an absence-asserted test fails if a
  money screen renders without the matching capability flag for
  every non-permitted role. [FR1.4] [FR10.3] [FR12.2] [NFR6.6]
- **CC-AC-BASIS** Every money figure carries a basis pill
  (`earned` or `realized`) and a completeness control
  (`have` of `of`) with a why-missing sheet. [FR10.1] [FR10.3]
- **CC-AC-STATUS-BUCKET** The status-bucket math
  (`EARNED_STATUSES`, `REALIZED_STATUSES`, `PIPELINE_STATUSES`) is
  restated inline in any test that asserts it; tests do NOT
  import the constants. [FR10.2]
- **CC-AC-I18N** Money figures, dates, and quantities render in
  Bangla digits by default. The Latin-digit allow-list covers
  record IDs, phone numbers, filenames, URLs, ISO dates, and
  version strings only. [FR11.1] [FR11.2]
- **CC-AC-AUDIT-IMmutability** A migration that re-grants
  `UPDATE` or `DELETE` on the audit table to the application
  role fails CI. [FR12.1] [NFR5.2] [TC9]
- **CC-AC-TENANT** A cross-tenant data access is impossible at the
  row level; absence-asserted tests cover every route. [FR1.5]
  [FR12.4]
- **CC-AC-COVERAGE** New or modified code carries unit tests
  sufficient to keep the consolidated line coverage ≥ 80 %.
  [NFR6.1] [TC5]
- **CC-AC-TYPESCRIPT-STRICT** New or modified code compiles under
  TypeScript strict (`strict`, `noImplicitAny`, `noImplicitReturns`,
  `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`). No
  `// @ts-ignore` without inline justification. [NFR7.1]
- **CC-AC-COMMENTS-AS-DESIGN** New modules carry a leading block
  comment documenting the design rationale; inline comments
  document decisions, not syntax. No `console.log` / `TODO` /
  `FIXME` / dead code in shipped code; CI fails on any of those
  markers. [NFR7.8]

## Epic family 1 — Capture

### US1.1 — Sign up and provision the business

**Persona:** `[P-Owner]`
**FR cluster:** FR1 (Authentication & Business Setup)
**Priority:** Must

As an Owner, I want to sign up with email + password and have my
business auto-provisioned so that I can start using the app on
day one without admin setup.

- **AC1.1.1** The Owner completes a sign-up form (email, password,
  business name, business phone, currency, default language)
  and is granted the Owner role automatically as the first user
  on the deployment. [FR1.1] [FR1.2]
- **AC1.1.2** A business profile is created with the supplied
  name, address, phone, currency, and default language. The
  business profile is the tenant boundary. [FR1.5]
- **AC1.1.3** Password recovery runs without a paid third-party
  service (no SaaS email gateway in MVP). [NFR5.1]
- **AC1.1.4** Every money-related screen on the resulting
  deployment renders the basis pill and the role-gate
  correctly for the Owner (CC-AC-BASIS, CC-AC-ROLE-GATE).

### US1.17 — Move an order through its status lifecycle

**Persona:** `[P-Owner]`, `[P-Staff]`
**FR cluster:** FR5
**Priority:** Must

As an Owner or Staff, I want to move an order through
`new → confirmed → packed → shipped → delivered → settled`

- **AC1.17.1** The status enum is exhaustive: `new`, `confirmed`,
  `packed`, `shipped`, `delivered`, `settled`, `cancelled`,
  `returned`, `partial`. No value is collapsed to a derived
  view and no value is a magic string. The production code
  uses a discriminated string-literal union with an exhaustive
  `switch` and a `never`-asserted default. [FR5.3]
- **AC1.17.2** `Cancelled` drops out of the realised bucket
  but remains visible in history. [FR5.6]
- **AC1.17.3** `Returned` moves the order to the returns
  bucket; physical-received is a separate, audited action
  (US2.8). [FR5.6] [FR4.4]
- **AC1.17.4** Every status change appends an audit row
  (CC-AC-AUDIT).
- **AC1.17.5** Status-bucket tests restate the
  `EARNED_STATUSES` / `REALIZED_STATUSES` / `PIPELINE_STATUSES`
  constants inline (CC-AC-STATUS-BUCKET).

### US2.2 — Run a courier settlement

**Persona:** `[P-Owner]`
**FR cluster:** FR6
**Priority:** Must

As an Owner, I want to run a settlement over a period and
review each consignment with a disposition so that I can
reconcile courier money without losing it to short

- **AC2.2.1** A settlement run lists every consignment for

  leaves the order at `delivered` with a basis pill

  [CC-AC-BASIS]
- **AC2.2.5** A `dispute` row keeps the order at `delivered`
  and surfaces the dispute on the order detail until the
  Owner resolves it. [FR6.3]
- **AC2.2.6** A `write_off` row requires a reason note and
  appends an audit row (CC-AC-AUDIT).
- **AC2.2.7** Status-bucket tests restate the constants inline
  (CC-AC-STATUS-BUCKET).

stock that actually came back.

### US3.7 — Operate the test suite and coverage floor

**Persona:** `[P-System]`, `[P-Owner]`
**FR cluster:** NFR6
**Priority:** Must

As the system, I want the test suite to enforce the
recognition-basis invariant, the role-gate, and the 80 %
coverage floor so that no merge weakens the binding
guarantees.

- **AC3.7.1** Consolidated line-coverage of custom
  application code ≥ 80 % before every merge to `main`.
  Coverage tooling is required in CI. [NFR6.1] [TC5]
  [CC-AC-COVERAGE]
- **AC3.7.2** The test suite preserves the prototype's
  mutual-blindness discipline: structural/arithmetic
  harnesses, rendering/click harnesses, flow harnesses,
  CSS-class reachability, contrast-off-tokens harnesses,
  and story-coverage parity. [NFR6.2]
- **AC3.7.3** Test-after ordering per layer: implement
  data + view + action → write the layer's tests → run
  the layer's tests + the full suite → confirm the 80 %
  floor still holds. [NFR6.3]
- **AC3.7.4** Mutation discipline: each truth-harness
  assertion is re-checked by reintroducing the defect
  it was written for; each mutation must be caught.
  [NFR6.4]
- **AC3.7.5** Critical regression-prone path coverage:
  every paste-parse flow test asserts the segment-
  isolation rule with multiple products, multiple
  variants per product, and common Bangla connector
  words. [NFR6.5]
- **AC3.7.6** Three-layer Role-gate test: the role ×
  capability gate is tested by absence over every route,
  not by the presence of a lock on one route. The Owner
  still reaches the audit trail and the daily card.
  [NFR6.6]
- **AC3.7.7** Test-data stability: tests run against a
  fixed seed clock; production uses `new Date()` for the
  live system but freezes the test clock. [NFR6.7]
- **AC3.7.8** Reverse-deploy gates: a regression in
  coverage, in CI, or in the recognition-basis / role-
  gate / audit-immutability invariants blocks the
  merge — not just a failed unit test. The gate is
  enforced in CI, not by review. [NFR8.4]

### US3.8 — Operate the code-style and architecture posture

**Persona:** `[P-System]`
**FR cluster:** NFR7
**Priority:** Must

As the system, I want the codebase to compile under
TypeScript strict and carry comments-as-design so that
the production surface matches the team's posture.

- **AC3.8.1** Full TypeScript with `"strict": true`,
  `"noImplicitAny": true`, `"noImplicitReturns": true`,
  `"noUncheckedIndexedAccess": true`, and
  `"exactOptionalPropertyTypes": true`. [NFR7.1]
- **AC3.8.2** `// @ts-ignore` is banned without an inline
  justification comment on the same line; `// @ts-nocheck`
  on the whole file is banned. JSDoc + `// @ts-check` is
  not a fallback. [NFR7.1] [CC-AC-TYPESCRIPT-STRICT]
- **AC3.8.3** Modern ES uniformly: `let`/`const`, arrow
  functions, template literals, `class`, destructuring,
  ES modules. `var` is banned. [NFR7.2]
- **AC3.8.4** Single top-level `package.json` (or
  workspace) with both runtime and test deps. [NFR7.3]
- **AC3.8.5** One registry per concern: `routes`, `actions`,
  `state` are typed registries. [NFR7.4]
- **AC3.8.6** State container is typed: schema,
  ownership, mutation rules. [NFR7.5]
- **AC3.8.7** Chrome binary path parameterised via env
  var or `chrome-launcher`. [NFR7.6]
- **AC3.8.8** Bundler + TypeScript transpiler (Vite or
  equivalent) at the first PR. [NFR7.7]
- **AC3.8.9** Comments-as-design-rationale: every
  module carries a leading block comment; inline
  comments document decisions, not syntax. No
  `console.log` / `TODO` / `FIXME` / dead code in
  shipped code; CI fails on any of those markers.
  [NFR7.8] [CC-AC-COMMENTS-AS-DESIGN]
